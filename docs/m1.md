# M1 — LightGBM on label-free pair features (DESIGN.md §5)

Status 2026-10-28. Owner: M1 modelling agent. **All runs below are `git_dirty=True`**: the agent was told
not to commit, so these runs cannot be adopted. Re-run them at a clean commit before adoption.

## What M1 is
- **Features**: `src/pairs.py` `assemble(pairs_df, groups=None, exclude=None, spec=, perm=)` builds them from
  the feature store manifest. The store had 9 groups and **358 features** at run time:
  CER, CONS, EXPR, KOPROT, LOC, PHEN, PPI, SEQ, plus HYPO.
  - Each gene-level column c gives `c__min` (NaN if either gene is missing) and `c__max` (nan-ignoring).
    The pair is lossless up to order, and "one gene missing" stays visible to the model.
  - Fitness-like columns (`smf|fitness`) also get `c__prod`.
  - Each `pair/*.npy` and `sim/*.npy` matrix gives a direct lookup `M[min(i,j), max(i,j)]`.
  - `HYPO__min/max` come from `hypomorph_a/b`. These are the real flags on training rows and 0 on eval rows.
  - Assembly is chunked (1M rows) and reads the matrices via `mmap_mode='r'`.
  - The manifest is snapshotted once per run, so feature groups added during a run do not change it.
- **Model**: `src/models/lgbm.py` + `scripts/run_m1.py`.
  - Binary LightGBM with uniform row weights.
  - Training rows are the fold's training pairs from `data.fold_split`. Pairs with a gene not in
    `genes.txt` are dropped: 4.6k–6.1k per fold, 26.5k pairs / 124 positives over the 5 folds; see Issues.
  - **Early stopping**: hold out 15% of the training genes, seeded by (inner seed, fold, model seed).
    Pairs touching those genes are the validation set and are removed from fitting. Maximum 2000 rounds,
    stop after 100 rounds without improvement, metric = AP. The reported fold is never used.
  - Seeds 0,1,2, averaged inside `evaluate()`.
- **Config check**: capped at 6 configs (`lgbm.CONFIGS`), run on the fold-0 inner split only
  (`results/m1/tuning.json`). Inner-validation AP ranged 0.1247–0.1299.
  - The pre-stated rule (maximum AP) chose `ff0.4`: feature_fraction 0.4, num_leaves 63, lr 0.05,
    bagging 0.8, min_data_in_leaf 200, λ2 = 1.
  - It beat the default by only 0.0007, so the choice is essentially a tie.
- **Symmetry**: two checks run on every fold.
  - Features: `assemble(b,a) == assemble(a,b)` exactly, for all eval rows.
  - Predictions: equal exactly on 20k swapped eval rows for every model.
  - `tests/test_pairs.py` covers the same, including an asymmetric variant that the check must catch.

### Gene-permutation negative control (DESIGN §6)
- **Setup**: the identities of the 1,924 dev genes are permuted in the gene → feature-row map. Every table
  and matrix is permuted consistently. One model seed.
- **Result**: M1 falls to **0.0708**. The pre-stated pass criterion is M1_perm ≤ B1 + 0.005 = 0.108,
  so it **PASSES**. Δ(perm − B1) = −0.033 [−0.040, −0.026].
- **C3 = 0.0219**, which is at prevalence (0.0215).
- C1 (0.133) and C2 (0.059) stay above prevalence. That is expected: a permuted feature vector is still a
  unique per-gene fingerprint, so the model can memorise the propensity of genes seen in training. This is
  B1-like behaviour, and it stays below B1.

compared, paired, against a matching seed-0 full reference (`M1_s0`). Δ = reference − ablated, so a

## Issues / notes for the PI
1. **Training pairs with genes outside `genes.txt`.**
   - `data.fold_split` training rows include 11 dev genes that are not protein-coding in PomBase, e.g.
     `SPAC186.04c` and `SPAC2E12.05` (pseudogenes).
   - That is 4.6k–6.1k pairs per fold, about 1%. DESIGN §1 says these are dropped.
   - M1 drops them itself and logs the count in the run JSON. Upstream (make_splits/data.py) should
     decide this once for all models.
2. **Short source aliases in the manifest.**
   - Manifest `sources` use short aliases (`biogrid`, `pombase`) rather than allowlist dataset ids
     (`biogrid_physical`, `pombase_orthologs`/`_protein`).
   - `pairs.source_violations` accepts an alias only if it is not itself a non-feature id and prefixes a
     use=feature id. It also rejects forbidden patterns (fypo, viability, ryan, string, GO, …) in
     `source_files`.
   - Because `pombase` also prefixes the universe-only `pombase_ids_viability`, the check relies on
     `source_files`. Exact dataset ids in the manifest would be cleaner.
3. HYPO__max carries real gain (0.0075; ablation Δ +0.003, CI just touching 0). The flags are 0 on all
   eval rows (tested), so this is the intended §1 de-confounding, not leakage.
4. M1 has no `init_score` (inner-fold B1 logit) and no propensity-ordered raw features. Both are listed in
   DESIGN §5 as M1 options/ablations and are left for M1N/M2.
5. The store was unchanged at the end of this work (same 50 files and sha256s as the headline run), so the
   headline run already reflects the current store. No re-run was needed.

```bash
.venv/bin/python scripts/run_m1.py --params tuned --save-models            # headline (3 seeds)
.venv/bin/python scripts/run_m1.py --params tuned --skip-full --ablate --permute   # seed-0 ablations + control
.venv/bin/python scripts/m1_universe_smoke.py --models-dir data/processed/models/m1/M1_ff0.4
.venv/bin/python scripts/m1_report.py --headline results/m1/report_<run>.json --ablation results/m1/report_M1_s0_<run>.json
# toy: prefix PSL_DATA_ROOT=data/toy PSL_RESULTS_ROOT=results/toy (after make_splits.py on the toy root)

```

(toy: `results/toy/m1/`). Models are in `data/processed/models/m1/M1_ff0.4/` (git-ignored).
